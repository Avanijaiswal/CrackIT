CRACKIT — PROJECT LOG
======================
A crowdsourced interview-experience platform. Users post structured interview
experiences (company, role, rounds, questions), interact socially (like/comment),
and search a company to see an aggregated report of what that company asks.

Tech: Python + MySQL, command-line interface (no web framework).

STEP 16 — Created project tables (users, companies, experiences, rounds,
          questions, comments, likes)

         1. users

Stores registered accounts.

id — primary key
name — user's display name
email — unique, used for login
password_hash — never store plain passwords; we'll hash it in Step 17
contributor_score — a simple gamification counter (increases as they post/comment)
2. companies

One row per company (Google, Amazon, TCS, etc.) — created dynamically as users post experiences about new companies.

id — primary key
name — unique company name
3. experiences

The core post — one interview experience shared by a user.

id — primary key
user_id — who posted it (links to users)
company_id — which company (links to companies)
role — job role/title applied for
outcome — Selected / Rejected / Pending
is_anonymous — whether to hide the poster's name when displaying
created_at — timestamp, auto-filled
4. rounds

Each experience can have multiple rounds (OA, Technical, HR, etc.) — one-to-many with experiences.

id — primary key
experience_id — which experience this round belongs to
round_number — 1st round, 2nd round, etc.
round_type — Technical / HR / Aptitude / GD / Managerial
5. questions

Each round can have multiple questions asked — one-to-many with rounds.

id — primary key
round_id — which round this question was asked in
question_text — the actual question
topic — tag like "DP", "SQL", "OOP" (filled by keyword-matching later)
6. comments

Threaded discussion under each experience post.

id — primary key
experience_id — which post this comment is on
user_id — who commented
comment_text — the comment itself
created_at — timestamp
7. likes

Tracks which user liked which experience (prevents double-liking, powers like counts).

id — primary key
user_id — who liked it
experience_id — which post was liked
- Created database/schema.py with a create_tables() function.
- Used cursor.execute("""...""") to run one CREATE TABLE IF NOT EXISTS per table.
- ENGINE=InnoDB used on every table — explicitly chosen because:
    - InnoDB actually enforces FOREIGN KEY constraints (MyISAM, the older
      alternative engine, silently ignores them).
    - Supports transactions (group multiple operations so they all succeed
      or all fail together) — not used yet, but relevant later when posting
      a full experience with multiple rounds/questions at once.
    - Handles simultaneous reads/writes safely (row-level locking) — relevant
      once multiple users can like/comment at the same time.
    - InnoDB is MySQL's default engine anyway (5.5+), but written explicitly
      so it's clear and intentional rather than relying on a silent default.
- Ran: python database/schema.py -> "✅ All tables created successfully."
- Verified all 7 tables visible in MySQL Workbench under crackit > Tables.

STEP 16b — Realized project needs proper layered architecture (discussion)
- Clarified the standard layers and what each is actually responsible for:
    - Model      -> plain structure only (e.g. a User class with just fields,
                    no logic, no SQL)
    - DAO         -> talks directly to the database with raw SQL (insert_user,
                    get_user_by_email, etc.), returns data/Model objects
    - Service     -> business logic sits here (e.g. check if email exists,
                    hash password, then call DAO to save) — decides "what
                    should happen"; DAO only knows "how to save/fetch"
    - Database    -> lowest layer, only opens/closes the connection
                    (already built: database/connection.py)
- Correct flow: main.py (CLI) -> services/ -> dao/ -> database/connection.py -> MySQL
                                            (models/ used by dao/service for structure)
- Clarified that schema.py (table creation) is NOT one of these layers — it's
  one-time/occasional setup/infrastructure code, a prerequisite the DAO layer
  depends on, not part of the request-handling flow. Decided to move it out
  of database/ to root-level schema.py, so database/ only ever means
  "how to connect."
- New planned structure:
    crackit/
    ├── database/          (connection.py only)
    ├── models/            (plain structure classes, one per entity)
    ├── dao/               (raw SQL per entity)
    ├── services/           (business logic per entity)
    ├── main.py             (CLI menu — calls services only)
    ├── schema.py           (moved out of database/, creates all tables)

PENDING DECISION — one file per layer (single dao.py, single service.py, single
models.py for everything) vs. one file per entity (dao/user_dao.py,
dao/experience_dao.py, dao/company_dao.py, etc.). Leaning toward one-file-per-
entity as the more standard/scalable approach, but not yet confirmed.

STEP 17 — Built user registration with password hashing
- Installed bcrypt: pip install bcrypt
- Updated requirements.txt.
- Created "services" folder (business-logic layer, sits between database
  layer and future CLI interface):
    - services/__init__.py (empty, marks folder as a package)
    - services/auth_service.py
- auth_service.py contains:
    - hash_password(plain_password): converts plain text into a secure,
      irreversible bcrypt hash (with random salt, so identical passwords
      produce different hashes).
    - register_user(name, email, plain_password): hashes the password,
      then inserts a new row into the users table.
- Used parameterized queries (%s placeholders + tuple of values) instead
  of directly inserting user input into SQL strings — this prevents SQL
  injection attacks.
- Used try/except/finally around the INSERT so failures (e.g. duplicate
  email, since email is UNIQUE) print a clear message instead of crashing,
  and the connection always closes regardless of success/failure.
- Ran: python services/auth_service.py
- Output: "✅ User 'Test User' registered successfully!"
- Verified in MySQL Workbench: users table now has a row with a long
  scrambled password_hash string — NOT the plain password.

STEP 18 — Built the login function
- Added login_user(email, plain_password) to services/auth_service.py.
- Used cursor(dictionary=True) so rows come back as dicts (access fields
  by name, e.g. user["name"], instead of positional tuples).
- Used a parameterized query (WHERE email = %s) to safely look up the user.
- Used bcrypt.checkpw(entered_password, stored_hash) to verify the password —
  this re-hashes the entered password using the same embedded salt and
  compares results. This is the correct way to verify a bcrypt hash;
  hashes are one-way and can never be "decrypted" back to plain text.
- Returns the user's dict on success (so the caller knows WHO logged in),
  or None if email not found / password wrong.
- Tested successfully:
    - Correct password -> "✅ Welcome back, Test User!"
    - Wrong password -> "❌ Incorrect password."

STEP 20a — Built company_service.py (find-or-create pattern)
- Created services/company_service.py.
- get_or_create_company(company_name):
    - First SELECTs by name to check if the company already exists.
    - If found, returns its existing id (no duplicate created).
    - If not found, INSERTs it and returns cursor.lastrowid (the new
      auto-generated id).
- This "find or create" pattern prevents duplicate company rows when
  multiple users post about the same company (e.g. "Amazon").
- Tested by calling get_or_create_company("Amazon") twice in a row —
  both calls returned the SAME id, confirming no duplicate was created
  on the second call.

STEP 20d — Built tagging_service.py (basic keyword-based topic tagging)
- Created services/tagging_service.py.
- TOPIC_KEYWORDS: a plain Python dictionary mapping topic names (DP,
  Trees, Graphs, Arrays, SQL, System Design, OOP, Behavioral) to lists
  of keyword phrases. Kept as Python data (not a DB table) for v1
  simplicity — easy to edit/expand without a migration.
- detect_topic(question_text):
    - Lowercases the question text for case-insensitive matching.
    - Loops through TOPIC_KEYWORDS, returns the first topic whose
      keyword appears in the text.
    - Falls back to "General" if nothing matches.
- This is intentionally simple keyword matching, not real NLP — good
  enough for v1, and this is exactly what will let the future "Company
  Intelligence" report group/count questions by topic.
- Tested with 4 sample questions:
    - "merge sort" question -> "General" (no keyword match yet, expected —
      keyword list can be expanded over time as real data comes in)
    - SQL question -> "SQL"
    - behavioral question -> "Behavioral"
    - OOP question -> "OOP"

STEP 23c — Added liking with toggle behavior
- Added toggle_like(user_id, experience_id) to social_service.py.
- First "toggle" function in the project — checks if a like already
  exists (SELECT), then decides: DELETE if it exists (un-like), INSERT
  if it doesn't (like). Prevents duplicate likes from the same user on
  the same experience, and allows un-liking.
- Used a plain (non-dictionary) cursor here deliberately — existing_like
  comes back as a tuple, accessed via existing_like[0] (position 0)
  instead of a dict key. Contrast with dictionary=True used elsewhere:
  plain tuples are fine for quick internal single-value checks; dict
  cursors are better when displaying named fields to a user.
- First DELETE statement in the project: deletes by the like's own
  unique id (found via the SELECT), not by re-matching user_id +
  experience_id again.
- Tested by running social_service.py twice in a row:
    - 1st run: "👍 Experience liked!" -> row appeared in Workbench
      (SELECT * FROM likes;)
    - 2nd run: "👎 Like removed." -> row disappeared from Workbench
  Confirms toggle works correctly in both directions.
